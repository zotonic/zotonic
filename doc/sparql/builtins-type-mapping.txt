SQL expression type mapping
===========================

The SQL generator walks SPARQL expression trees bottom-up. Every generated
expression records:

    sql       PostgreSQL expression
    type      logical value type
    source    argument, column, expression or jsonb
    defined   whether an OPTIONAL/VALUES binding is defined

Values keep their storage representation until an operator or built-in needs a
concrete type. In particular, JSONB selectors use #> and are not converted when
they are only projected.


Value types
-----------

    any         Type is not yet known; commonly an unbound/query argument
    boolean     PostgreSQL boolean
    datetime    PostgreSQL timestamptz
    float       PostgreSQL real or double precision
    integer     PostgreSQL integer/bigint family
    number      Numeric supertype used before integer/float is resolved
    text        PostgreSQL text
    uri         IRI text value
    id          Zotonic resource id stored as an integer
    ids         Array of resource ids
    list        Array/list value
    fts         PostgreSQL tsvector search value
    fulltext    Trigram/full-text search value

Resource bindings are represented separately from scalar expressions as a
resource table alias. This prevents an rsc.id from automatically becoming a
numeric RDF literal in places where the binding is known to be a resource.
An id-typed property remains ambiguous: its SQL storage is numeric, while its
RDF interpretation can be an IRI.


Operators
---------

Arithmetic operators require numbers and produce a numeric result:

    - <number>               -> <number>
    + <number>               -> <number>
    <number> - <number>      -> <number>
    <number> + <number>      -> <number>
    <number> * <number>      -> <number>
    <number> / <number>      -> <number>

If either known operand is a float, the result is a float. Otherwise the result
is integer unless an operand is only known as number.

Boolean operators require booleans:

    ! <boolean>              -> <boolean>
    <boolean> && <boolean>   -> <boolean>
    <boolean> || <boolean>   -> <boolean>

Comparison operators coerce both operands to a common compatible type and
return boolean:

    =  !=  <  <=  >  >=

Compatibility currently includes integer/float/number, text/uri and
integer/id. Incompatible known types return an incompatible_types error.
Parameterized arguments are left for PostgreSQL to infer from the surrounding
expression where possible.


JSONB coercion
--------------

JSONB property expressions retain #> output until a concrete value is needed.
They are then mapped as follows:

    text, uri       jsonb #>> '{}'
    datetime        (jsonb #>> '{}')::timestamptz
    integer, id     jsonb::bigint
    float           jsonb::double precision
    number          jsonb::numeric
    boolean         jsonb::boolean

isLITERAL and isNUMERIC inspect jsonb_typeof directly so that structured JSON
objects and arrays are not treated as RDF scalar literals.

isIRI and isURI use resource bindings and the uri value type. A JSONB property
declared as uri additionally checks that its stored value is a JSON string.
isBLANK returns false for SQL values because no SQL expression type represents
a blank node.


Built-ins and constructors
--------------------------

Each supported built-in declares argument and result types in
z_sparql_sql_function.erl. Arguments are coerced before the PostgreSQL
expression is emitted. The common pseudo-type used by COALESCE and IF requires
their value alternatives to resolve to a compatible type.

UUID produces a uri value containing a `urn:uuid:` IRI; STRUUID produces text.
Constant IRI/URI constructor strings are resolved by the query planner while
BASE is available. Resource and uri values pass through unchanged. Text values
also pass through, but dynamic relative values are not resolved against BASE.

Well-known XSD constructor IRIs are handled separately by
z_sparql_sql_datatype.erl. They map string, boolean, integer variants, decimal,
float, double, dateTime and dateTimeStamp to PostgreSQL casts. Date/time
construction also accepts integer Unix seconds.

Aggregates declare their input and result types in
z_sparql_sql_aggregate.erl. MIN, MAX and SAMPLE preserve their argument type;
SUM and AVG require numeric input; GROUP_CONCAT coerces input to text.
